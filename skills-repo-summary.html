01 · At a glance

A small operating system for engineering work

The collection organizes agent work around a few durable moves: choose a route, sharpen decisions, turn the result into buildable work, implement in small slices, and review the outcome. Several skills are supporting disciplines rather than steps in the main route.

02 · Main route

Idea to ship

The default path for work that begins as an idea and ends as a reviewed change. Branch only when the work needs a different kind of evidence or coordination.

1

Orient

Use ask-matt; run setup-matt-pocock-skills once for a new repo.

2

Sharpen

Interview the idea with grill-with-docs, keeping terminology clear with domain-modeling.

3

Shape

Use to-spec for a build brief, then to-tickets for vertical slices.

4

Build

Use implement; it drives focused work with tdd.

5

Review

Run code-review against both repository standards and the originating spec.

6

Keep clean

Apply unslop to writing and use architecture upkeep when the codebase needs it.

The route is a guide, not a mandatory pipeline. A small, well-defined change may go straight to implement; a large effort may need wayfinder first.

03 · Choose a starting point

Match the situation to the first move

The work is an idea or request

Use this when the desired outcome is still being shaped.

  • Unsure which route fits: ask-matt
  • Need a rigorous interview: grilling
  • Need a durable paper trail: grill-with-docs

Something is broken or incoming

Use this when the work arrives as a problem rather than a settled plan.

  • Hard bug or regression: diagnosing-bugs
  • Raw issue or external PR: triage
  • Existing merge or rebase conflict: resolving-merge-conflicts

The effort is too large or too foggy

Use this when one session cannot yet see the route to the destination.

  • Map linked decisions first: wayfinder
  • Need external facts: research
  • Move context between sessions: handoff

05 · Maintainer notes

Keep the collection understandable

Repository shape

.agents/
└── skills/
    ├── <skill-name>/
    │   ├── SKILL.md
    │   ├── agents/openai.yaml
    │   └── supporting docs or scripts
    └── ...

Every local skill has a primary SKILL.md. Agent-facing display metadata lives in agents/openai.yaml where provided; some skills also carry formats, templates, reference notes, or scripts.

Maintenance rules visible in this snapshot

  • Keep each skill's purpose and trigger condition explicit in its front matter.
  • Use the router and workflow descriptions as the map; keep individual skills focused on one job.
  • Preserve the distinction between thinking, shaping, building, and maintenance work.
  • Keep domain vocabulary in the domain-modeling layer and module-shape vocabulary in codebase-design.
  • Apply the writing-quality pass to maintainer-facing docs as they change.
